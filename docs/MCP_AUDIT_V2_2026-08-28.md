# MCP & Plugin Audit — v2 reality, 2026-08-28

## Scope

This document supersedes `PLUGIN_AUDIT_2026-08-28.md` (which was based
on **v1 telemetry** and is now marked v1-only). The current Mavis
install is `Mavis 3.0.67.128`, running a **v2 runtime** with an
MCP-based architecture that the original audit did not look at.

Verified facts as of 2026-08-28 12:30 local (Asia/Irkutsk).

## v2 architecture: what we found

### 1. Active runtime is MCP-based, not opencode-plugin-based

Direct evidence from process listing (PID 16572):

```
"C:\Users\hopt\AppData\Local\Programs\MiniMax Code\MiniMax Code.exe" \
  "C:\Users\hopt\AppData\Local\Programs\MiniMax Code\resources\app.asar\
   node_modules\@mavis\agent-tools\dist\desktop\matrix-mcp-stdio.js"
```

v2 spawns MCP servers as child processes of an Electron NodeService
utility process (PID 30648). The `~/.minimax/agents/mavis/opencode/plugins/`
directory inspected by the v1 audit is **not used by v2** — those
files are leftover v1 artifacts.

### 2. MCP server registry is in `~/.minimax/mcp/mcp.json`

5 servers defined; 1 currently active. All have `enabled: true` and
`configured: true`. Status column is from a 2026-08-28 process + port
check, not from the config.

| Server      | Transport                              | Builtin  | Active right now | Fallback                           |
| ----------- | -------------------------------------- | -------- | ---------------- | ---------------------------------- |
| `matrix`    | stdio (asar `@mavis/agent-tools`)      | yes      | **yes** (PID 16572) | none                             |
| `playwright`| stdio (`npx @playwright/mcp@0.0.70`)   | yes      | no               | spawn on demand                    |
| `cu`        | HTTP `127.0.0.1:15321/mavis/mcp/cu`    | yes      | **no** — port 15321 not listening | **none** — desktop control broken |
| `trash`     | HTTP `127.0.0.1:15321/mavis/mcp/trash` | yes      | **no** — port 15321 not listening | `mavis-trash.cmd` CLI works      |
| `bridge`    | stdio (`O:\user files\...\bridge-mcp-server.mjs`) | no | no               | direct CLI in PATH                 |

`mavis-trash` has a documented CLI fallback in its own description
("In shell commands, use `mavis-trash <path1> <path2> ...` directly —
no need to go through `mavis mcp call`"). `cu` (Computer Use) does
not, so desktop control via MCP is currently unavailable on this
Mavis install until 15321 comes back.

Path bug worth noting: the `matrix` MCP's `args` contains
`resources\resources\matrix-mcp-cli\index.js` — a duplicated
`resources` segment, same malformed pattern as the `mavis.js`
plugin stub and the `daemon\cli.js` path. v2 must resolve these
through some asar-internal layer that strips one of the segments.

#### Known gaps in token telemetry

- `model` is `None` in every row. The v2 logger does not capture
  which model was used per turn, even though `llm_response_identifiers`
  events in `~/.minimax/v2/observability/logs/runtime-*.log` do
  carry the model name. This is a wiring gap, not a data gap.
- `cost_usd` is `0.0` in every row. The cost calculator is not
  connected; only token counts are aggregated.

Both gaps are addressable from this codebase (add `model` to the
insert path, wire cost calculator). They are not blocking for
optimization work — token counts are enough to prioritize.

### 5. Port 15321 is not listening

Tested `127.0.0.1:15321/mavis/mcp/cu`, `/mavis/mcp/trash`, and
`/mavis/api/v1/health` — all return "Unable to connect to the
remote server" within 3 s. The `cu` and `trash` MCPs are therefore
non-functional via HTTP. `trash` has a documented CLI fallback;
`cu` does not.

This is the same class of finding as the v1 plugin audit: many
"configured" services are not actually serving. The difference is
that v1 was a 7-plugin directory with 1 active; v2 is a 5-MCP
config with 1 active and 2 with a CLI fallback.

## What this means for `minimax-code-token-optimizer`

### Direct consequences

- **`scripts/apply-mavis-opencode-optimizations.mjs`** targets
  `…/daemon/node_modules/@mavis/opencode-plugin/index.js`. This
  path is irrelevant in v2 (the bundle patcher location is
  `app.asar`, and the v2 plugin loader is the SQLite + mcp.json
  pipeline). The patcher is a **no-op on this Mavis** for the same
  reason it was a no-op on the v1 install audited earlier.
- The "71% input-token reduction" cited in the README is delivered
  in v1 through the patcher; in v2 the equivalent is **prompt cache
  recovery**, which is already happening natively (146M cache_read
  vs 10.8M input over 44 days). The README's claim does not apply
  to v2 users.
- `cleanup-backups.mjs` (PR #1) and the lock-check in
  `apply-mavis-opencode-optimizations.mjs` are still relevant —
  they protect the install from a future v2-rewrite of the patcher
  or a rollback to v1.

### Indirect consequences

- Most items in `OPTIMIZATION_BACKLOG.md` (H0, H1, H2, M1, M2, L1)
  were framed around v1 mechanics (opencode plugins, bundle patch,
  context-budget plugin, policy.json). They need a v2 rewrite.
  See the rebuilt `OPTIMIZATION_BACKLOG.md` in this PR.
- M1 (skill content trimming) and L1 (compaction tuning) are
  **now measurable** via the SQLite `local_runtime_token_usage`
  table. The `mavis usage session <id> --json` CLI mentioned in
  the README is broken, but the underlying data is in the DB.
