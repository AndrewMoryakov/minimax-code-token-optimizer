# Plugin Audit — 2026-08-28

## Scope

Runtime audit of which opencode plugins are actually loaded by the current
Mavis install (`Mavis 3.0.67.128`). Direct evidence: telemetry produced by
plugins during a 19-minute real workload.

Not a code review. Not a benchmark. Just: which `.js` files in
`~/.minimax/agents/mavis/opencode/plugins/` are emitting log events, and which
are dead.

## Indirect confirmations

These three independent signals all agree with the log count.

1. **`mavis.js` is a 211-byte auto-generated stub.** Its body is exactly:
   ```js
   // Auto-generated by Mavis daemon — do not edit
   export { default } from "C:\\Users\\hopt\\AppData\\Local\\Programs\\MiniMax Code\\resources\\resources\\daemon\\node_modules\\@mavis\\opencode-plugin\\index.js"
   ```
   The re-export target contains `resources\resources\` (duplicated segment) —
   a malformed path. This stub therefore fails to load silently rather than
   producing a hook subscriber.

2. **`opencode.json` lists only `minimax` as a provider.** No `openrouter`
   provider entry. If `openrouter-lifecycle.js` were loaded, it would either
   register the provider or emit an error event on startup. Neither happens.

3. **`policy.json` at `~/.minimax/agents/mavis/context-budget/config/` is
   inactive.** It declares `profile: "max"` and OpenRouter-routing rules.
   `context-budget.js` is the only code that would consume it, and that file
   is not loaded. The config is valid JSON, but it has no effect.

The only log event families in the 19-minute window are:

- `http_request` (1)
- `permission_final_args` (1)
- `tool_execute_after_args` (1)
- `request_guard_over_budget` (65)

The first three are baseline `opencode-plugin` framework events (one per
session start / first tool call), the rest are all `request-guard` events.
No other plugin's hooks fire.

## Why this matters for the patcher

The bundle patcher
(`scripts/apply-mavis-opencode-optimizations.mjs`) targets
`…/daemon/node_modules/@mavis/opencode-plugin/index.js`. That path is the
same malformed one referenced by `mavis.js`. It does not exist on disk:

```
$ ls 'C:\Users\hopt\AppData\Local\Programs\MiniMax Code\resources\resources\daemon\node_modules'
→ does not exist
```

The actual Mavis daemon code is bundled inside
`MiniMax Code\resources\app.asar` (475 MB), which the patcher does not
extract or modify. On the current Mavis version the patcher therefore runs
but cannot find its target, so it logs a "no-op" exit and writes nothing.

## What this means for the README's "71% reduction" claim

The reduction is delivered through three layers, per the README:

1. Bundle patch inside `app.asar` (replaces the `opencode-plugin` index.js
   body with one that instruments every hook).
2. Plugin files in `~/.minimax/agents/mavis/opencode/plugins/`.
3. `policy.json` in `~/.minimax/agents/mavis/context-budget/config/`.

On `Mavis 3.0.67.128` only layer 2's *first* file (`request-guard.js`) is
active. Layers 1 and 3 are inert: the patcher can't write to `app.asar`,
and `context-budget.js` (the consumer of layer 3) is not loaded.

The headline 71% figure therefore does not apply to this Mavis build. Any
empirical token reduction in a session that runs on this Mavis is coming
from `request-guard` in `observe` mode, which only logs oversized bodies
without acting on them. **Net runtime effect: zero.**

## What I could not verify

- I did not extract or read `app.asar`. The contents of the bundled
  `opencode-plugin/index.js` (what the patcher wants to rewrite, and what
  `mavis.js` is trying to import) are unknown to me.
- I did not restart Mavis during the audit. The 19-minute window in
  `plugin-2026071423.log` is one continuous session, not a representative
  sample of all plugin load paths.
- I did not look at `opencode/dist` internals. It is possible the plugin
  loader resolves `mavis.js` via a different mechanism (e.g. `node_modules`
  walking) that bypasses the malformed `opencode.json` field. This would
  explain how `request-guard.js` gets loaded when the registered plugin
  name is only `"mavis"`.

These limits are not blocking: the log evidence alone is sufficient to
conclude that 6 of 7 non-stub plugins are inactive. The unresolved
questions are about *why* and *how to fix*, not *whether* the finding is
correct.
